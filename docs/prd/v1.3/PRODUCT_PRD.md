## 一、v1.3 要解决的问题（从使用场景提炼）

> 用户原话（2026-10-05）：
> - "我平时，主要还是手机，安卓手机。"
> - 网站定位是"线上简历 + 内容自留地"，内容由用户自主维护（博客、项目、收藏 5 品类、一闪念）
> - 收藏夹内容"估计是需要我自己手写"；一闪念是碎片化随手记录

### 问题 1：内容更新被绑定在"电脑 + 本地开发环境 + git"（核心问题）

- **现象：** 当前所有内容存放在 `src/content/` 的 markdown 文件里，更新内容 = 本地编辑文件 + `git push` + 等 Cloudflare Pages 构建部署
- **本质：** 网站没有**内容管理入口**。用户在手机上（主要使用场景）无法更新任何内容；即便在电脑上，也必须打开项目、跑开发环境、提交代码——"随手记"这个核心诉求完全无法满足
- **为什么没做到：** v1.0~v1.2 全部聚焦"展示层"（页面、状态、动画），从未考虑"内容生产层"（如何让用户方便地写内容）

### 问题 2：内容生产路径与"个人自留地"定位不匹配

- **现象：** 一闪念（notes）是碎片记录，设计上就是"想到就记"，但实际要经历完整 git 流程
- **本质：** 内容生产频率低、但要求"随时随地可达"。需要的是一个轻量、移动端可用的内容编辑入口
- **结论：** v1.3 的核心是给网站加一个**内容管理后台**

## 二、方案对比与决策（2026-10-05 已与用户确认）

| 方案 | 说明 | 成本 | 架构影响 | 决策 |
| --- | --- | --- | --- | --- |
| A：GitHub 手机 App 直接编辑 | 零成本，但 markdown 纯文本编辑体验差，长文/图片管理难受 | 极低 | 无 | ❌ 否 |
| **B：Decap CMS**（选定） | 免费开源、内容仍存 markdown + Git、纯前端管理界面挂在自己域名下；Astro 官方文档有集成指南；认证用 GitHub OAuth + Cloudflare Pages Functions 代理（免费） | 低（1 天级） | **零**（保持 SSG） | ✅ **采用** |
| C：Cloudflare D1 + Functions 自建全栈后台 | 完全可控、可自定义移动端体验，但需要鉴权/数据库/API/前端全套，一周级工程 | 高 | 大（SSG → SSR/混合） | ⏸ 留待未来大版本逐步改造 |

**v1.3 范围**：方案 B。全栈改造（方案 C）明确不在本版本，等需要更新大版本时另行规划。

### 体验验证结论（2026-10-05 用户真机实测）

- 用户用安卓手机打开 Decap 官方免登录 demo，实测结论："**确实可以，就是不像手机 App 那样好操作。先这样吧，之后不行再说。**"
- 结论：方案 B 手机端**可用**（达标），体验预期已对齐（Web 界面 vs 原生 App 的差距可接受）
- 备选记录：若后续手机体验无法接受，备选 **Sveltia CMS**（Decap 继任者分支，宣传移动端更优、配置兼容）——本版本不采用，仅记录

## 三、v1.3 候选功能清单（按优先级）

> 以下按优先级分组，请用户勾选哪些做、哪些不做。技术方案已核实（Astro v7 官方文档支持 Decap CMS；Cloudflare Pages Functions 承载 OAuth 代理已有成熟先例）。

### P0 — 管理后台核心接入

#### 1. Decap CMS 管理入口（/admin）

- **说明：** 接入 Decap CMS，在 `https://philia093.ink/admin` 提供管理界面
- **实现：**
  - `public/admin/index.html`（加载 Decap CMS 前端）+ `public/admin/config.yml`（后端配置 + 集合定义）
  - 8 个内容集合完整映射：blog / projects / books / music / novels / videos / links / notes
  - **字段级对齐现有 zod schema**（`src/content.config.ts`）：标题、日期、标签、分类枚举、评分、状态、draft/visible 等全部可编辑，保证编辑保存后构建不炸
- **验收：** 登录后在手机上打开 /admin，能浏览 8 个集合、新建/编辑/删除内容条目，保存后 GitHub 仓库出现对应 commit

#### 2. GitHub OAuth 登录

- **说明：** 管理后台必须认证，只有本人能操作
- **实现：**
  - 用户在 GitHub 创建 OAuth App（Settings → Developer settings → OAuth Apps，回调指向本站 /api/auth/callback）
  - Cloudflare Pages Functions 实现 OAuth 代理（`/api/auth`、`/api/auth/callback`），校验 state、交换 token
  - `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` 作为 Cloudflare Pages 环境变量（**绝不写入仓库**）
- **验收：** 打开 /admin → 点"Login with GitHub" → 授权 → 进入管理界面；未登录访问被拦截
- **注意：** OAuth App 创建需用户在 GitHub 网页端操作（授权自己账号即可，单用户场景）

#### 3. 图片上传与媒体库

- **说明：** 封面图（cover）等图片直接在后台上传，不再需要手动放仓库
- **实现：** Decap `media_folder` 指定统一图片目录（如 `public/uploads`），cover 字段用 image widget；保存时图片随内容一并 commit
- **验收：** 后台给博客/项目/收藏条目上传封面图 → 保存 → 线上图片正常显示

### P1 — 移动端体验（用户主场景是安卓手机）

#### 4. 安卓手机实际可用性验证与适配

- **说明：** 在真实安卓浏览器验证 /admin 的编辑、上传、保存全流程可用；对不适配的控件做针对性样式修正
- **验收：** 安卓 Chrome 浏览器内完成"新建一闪念 → 保存 → 手机浏览器看到线上更新"全链路

#### 5. /admin 添加到主屏幕（PWA 化）

- **说明：** 给 /admin 补 manifest + 图标，安卓可"添加到主屏幕"，点开像独立 App，强化"随手记"体验
- **实现：** 轻量 PWA 支持（manifest + apple-touch-icon / 安卓图标），不引入复杂 Service Worker（避免与现有缓存策略冲突，先不加 SW 或仅极简）
- **验收：** 安卓浏览器"添加到主屏幕"后，桌面图标点开直达 /admin 登录页
- **备注：** Service Worker 涉及缓存策略，与 EdgeOne/Pages 缓存叠加需谨慎，本版本**默认不加 SW**，仅 manifest+图标

#### 6. 本地开发模式

- **说明：** 本地 `astro dev` 也能调试后台，不依赖线上 OAuth
- **实现：** 本地代理 GITHUB 回调（如 Vite 插件/简单代理），或文档说明"本地改 config 指向线上回调"的调试方式
- **验收：** 本地能跑通"编辑→保存→本地预览"调试链路（验收标准可放宽：以文档说明可用方式为准）

### P2 — 治理与文档

#### 7. 后台使用与管理指南文档

- **说明：** 按用户文档偏好（"能 100% 复刻"），在 `docs/` 新增 `decap-cms-guide.md`：OAuth App 创建步骤、环境变量配置、config.yml 字段说明、手机端使用说明、常见问题
- **验收：** 按文档从零复刻后台接入不依赖记忆

#### 8. 保存→自动部署链路验证

- **说明：** 后台保存内容 → GitHub commit → Cloudflare Pages 自动构建部署 → EdgeOne 缓存刷新，全链路验证线上更新时效
- **注意：** EdgeOne 有缓存，需确认内容更新后线上可见（可能需要缓存规则调整或手动刷新机制）
- **验收：** 后台改一条内容 → N 分钟后线上可见更新

#### 9. 安全复核

- **说明：** 后台安全边界检查：config.yml 无密钥、OAuth 回调校验 state、repo 权限最小化（OAuth App 只授权本仓库或个人）、/admin 页面无敏感信息泄露
- **验收：** 安全清单逐项通过

## 四、风险与注意事项（提前说明，不隐藏）

- **保存即部署**：后台每次保存都会触发 GitHub push → Pages 构建（约 1-2 分钟），频繁编辑会多次构建。个人使用量级无问题
- **字段映射是最大返工点**：Decap 的 widget 类型（datetime/select/list/boolean/number）与 zod schema 必须逐一对齐，任何一个字段类型不匹配会导致保存后构建失败（有 zod 校验兜底，失败会明确报错，可修）
- **示例内容**：继续保留（真实内容补齐后删除，沿用 v1.2 决策）
- **Decap CMS 维护状态**：开源社区维护（Decap Turbo 为付费增强版，我们不需要），免费版功能完全够用
- **手机端体验预期**：Decap 界面偏桌面设计，手机上"能用但不算丝滑"——这正是方案 C（全栈自建）留待未来的原因
